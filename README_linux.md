# MikuSB on Linux and Proton

The Linux server can be started from source. The original Windows client under Proton has **not been verified** with this checkout. In particular, setting a proxy environment variable does not guarantee that the game's SDK and game sockets use it. A Windows Steam client reached the lobby using a Windows-only runtime redirect hook; that result does not establish Proton compatibility.

## Choose the setup that matches your server

If MikuSB is already running on a remote VPS, use [Steam Deck or CachyOS client setup for the VPS](#steam-deck-or-cachyos-client-setup-for-the-vps). On the client device, skip the local server, localhost SOCKS5, `ALL_PROXY`, and local certificate commands below. Those are for running and testing a server on the same machine.

If you want to run MikuSB on this Linux machine, follow the local server and SOCKS5 sections below.

## Start the server

Install the .NET 10 SDK, Python 3, and obtain compatible resource data separately. From the repository root:

```bash
python3 tools/setup.py --resources /path/to/resource-data
sh start-server.sh
```

Keep the server running. Setup creates the Git-ignored `Config/Config.local.json`; edit it to change settings. See [local setup](docs/setup.md) for details. The default local endpoints are game TCP `127.0.0.1:21000`, SDK HTTPS `127.0.0.1:21500`, `:13443` and `:31443`, and SOCKS5 `127.0.0.1:18888`. `Proxy.Enabled` must be true. If `Proxy.Port` is changed, the server also retains the 18888 listener.

## Check the SDK and proxy

With the server running, test the SOCKS5 path using curl:

```bash
curl --noproxy '' --socks5-hostname 127.0.0.1:18888 -k \
  https://xgsdk.xoyo.games:13443/getGameConfig
```

A JSON response and a `SOCKS: ...` line followed by an SDK request in the server console show that this test reached the local server. `--socks5-hostname` sends the hostname to the proxy, which needs it to match the configured domain list. `-k` disables certificate verification for this diagnostic only; it does not configure Proton or prove the client trusts the server. The server forwards non-target domains through the proxy, so inspect destinations before sending traffic through it.

The proxy implements SOCKS5, not HTTP CONNECT. For a client component that actually honors proxy environment variables, this Steam launch option is a possible diagnostic:

```text
ALL_PROXY=socks5h://127.0.0.1:18888 %command%
```

This is not a complete client setup. Do not assume Steam, Proton, the SDK, or every game socket honors `ALL_PROXY`. Direct connections bypass this proxy. The Windows launch uses an injected DLL to redirect direct SDK and game connections; the provided launcher uses Windows APIs and there is no verified Proton equivalent here. Do not enter real account credentials while testing local routing.

## Certificates and login diagnosis

The SDK creates self-signed TLS certificates in `MikuSB/bin/Debug/net10.0/sdk-certs/` when started with the script above; published builds place them in `sdk-certs` next to the application. The default wildcard certificate is `wildcard.xoyo.games.pfx`, with its public certificate exported as `wildcard.xoyo.games.pem`. Existing PFX certificates without CA constraints are replaced when the server starts so Linux trust tools can include the certificate in their generated CA bundle. Other hostnames get their own PFX and PEM on TLS handshake. PFX files contain private keys and should remain local; PEM files contain public certificates only. These self-signed certificates are installed as trust anchors by the VPS client setup below. Proton's separate certificate store still needs client testing.

To check the local wildcard certificate with verification enabled instead of `-k`:

```bash
curl --noproxy '' --socks5-hostname 127.0.0.1:18888 \
  --cacert MikuSB/bin/Debug/net10.0/sdk-certs/wildcard.xoyo.games.pem \
  https://xgsdk.xoyo.games:13443/getGameConfig
```

This verifies curl's connection only; Proton may use a different trust store or certificate policy. Use the PEM matching the requested hostname and keep the files generated by your own server.

If login fails, check the server logs for `/getGameConfig`, `/seasun/config`, `/seasun/login`, `/seasun/loginByToken`, `/account/query-uid/{appId}`, and `/seasun/getAccountInfoForGame`. HTTP `200` alone does not mean SDK authentication succeeded; inspect the server's `SdkAuth` accepted/rejected messages for the account lookup outcome. No relevant request indicates a routing or TLS boundary before that handler. The handler accepts an email and creates a local account when `ServerOption.AutoCreateUser` is enabled; token login requires an existing account. These handler behaviors do not establish that a particular Proton client sends a compatible request. Do not share credentials, tokens, or request bodies when diagnosing.

The existing [Windows launch investigation](docs/local-client-launch.md) records the socket redirection and port mapping used for the verified Windows lobby. A fresh Proton run is needed to determine its routing, TLS trust, request format, and game-connection requirements.

## Steam Deck or CachyOS client setup for the VPS

The VPS exposes the MikuSB SDK and game ports directly to the internet; its SOCKS proxy remains loopback-only. After downloading Snowbreak, download the setup script on the client device and run it:

```bash
mkdir -p ~/.local/share/mikusb-vps
curl -fsSL https://raw.githubusercontent.com/SalmanTKhan/MikuSB/dev/tools/client/setup-cachyos.sh \
  -o ~/.local/share/mikusb-vps/setup-cachyos.sh
chmod 700 ~/.local/share/mikusb-vps/setup-cachyos.sh
bash ~/.local/share/mikusb-vps/setup-cachyos.sh
```

The script embeds the VPS's public wildcard trust certificate, adds it to the system trust store, maps `xgsdk.xoyo.games` to the VPS address in `/etc/hosts`, and checks SDK TLS with curl. It does not connect to the VPS over SSH and needs no Steam launch option. The game server list advertises the VPS IP for gameplay. Use `MIKUSB_VPS_HOST=laima.ddns.net bash ~/.local/share/mikusb-vps/setup-cachyos.sh` to resolve the DDNS A record instead of the default `192.227.172.144`.

Editing `/etc/hosts` and installing a trusted certificate require administrator access. On SteamOS, the script temporarily disables the read-only root filesystem and reenables it when it exits. It will ask for the Deck's sudo password; set one through the Steam Devkit Management Tool first if none is configured. On CachyOS it uses the normal sudo prompt.

For the Deck-to-VPS setup, allow inbound TCP 5200 for gameplay and 21500, 13443, 18443, and 31443 for SDK HTTPS. The Deck connects directly to the VPS; do not start a local server or configure the local SOCKS5 proxy for this setup. Do not expose SOCKS5 port 18888. To undo the setup, remove the line tagged `MikuSB VPS SDK routing` from `/etc/hosts`, remove `/etc/ca-certificates/trust-source/anchors/mikusb-vps.crt`, and run `sudo update-ca-trust extract`. Successful SDK curl verifies network and certificate routing; gameplay still needs testing in Snowbreak.
